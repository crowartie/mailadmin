# Разбор надёжности веб-почты, 19.09.2026

Документ написан для передачи: по нему другой человек (или другая нейросеть) может
**повторить разбор независимо** — не веря выводам ниже на слово, а проверив их заново.
Поэтому здесь есть не только «что нашли», но и «где смотрели» и «чем проверяли».

---

## 1. Что это за система

Самописная веб-почта и админка **mailadmin**: Laravel 11 + Inertia + Vue 3 поверх iRedMail
(Postfix + Dovecot + Amavis/SpamAssassin + ClamAV). Заменяет SOGo и iRedAdmin.

| | сервер | домен | ящиков | почты на диске |
|---|---|---|---|---|
| боевой | `192.168.30.111` | mail.innotec.su | ~112 | 188 ГБ |
| второй | `192.168.100.93` (MAIL01) | mail.deltaservices.ru | немного | 43 МБ |

Доступ по SSH: пользователь `admin1`, ключ уже установлен. MAIL01 виден только с рабочего
ПК (с .111 туда маршрута нет).

Приложение живёт в `/opt/mailadmin`, отдаётся не через PHP-FPM, а через **Octane
(RoadRunner)** на `127.0.0.1:8000`, nginx проксирует. Копия для тестов — `/opt/mailadmin-test`
(боевой ставится с `--no-dev`, PHPUnit там нет и быть не должно).

### Постоянные ограничения (нарушать нельзя)

- **Почта не должна сломаться без возможности восстановления.** Любая правка потока почты —
  только с проверкой доставки под рукой.
- SSH наружу не открывать.
- Пароли ящиков меняет только администратор, самообслуживания нет.
- Вложения — только просмотр, без правки.
- Индексаторы днём работают с пониженным приоритетом.
- Рабочие копии репозитория — только в `C:\Users\User\mailadmin-work`, не во временных папках.
- Перед коммитом проверять `git status --short | grep '^ D'` — удалений быть не должно
  (16.09 коммит однажды снёс 197 файлов).

## 2. С чего начался разбор

Сотрудник (san@innotec.su) сообщил: «почта письма удаляет сама» — переслал письмо коллеге
с телефона, а в «Отправленных» его нет.

Разбор по журналам показал: письмо **ушло и было доставлено**, но копию в «Отправленные»
телефон загрузить не смог. Отправка (SMTP) и сохранение копии (IMAP APPEND) — две
независимые операции, обе выполняет клиент, и сервер их никак не связывает. Связь рвалась,
первая операция прошла с пятой попытки, вторая не прошла вовсе.

Отсюда и признак, по которому дальше искали **все** остальные слабые места:

> **Где результат зависит от второго шага, который может тихо не выполниться,
> а человеку при этом сказано, что всё хорошо?**

Это и есть определение «надеяться на удачу». Ищем не ошибки в коде, а места, где
**отсутствие ошибки не означает успеха**.

## 3. Как искали (методика — её и надо повторить)

1. **Прочитать путь отправки целиком**, от контроллера до IMAP: `ComposeController::send`
   → `Outgoing::send` → `afterSend`. Искать `catch`, которые ничего не сообщают.
2. **Прогнать поиск по проглоченным исключениям.** Скрипт `scan_catch.py` (лежит в рабочей
   папке, не в репозитории) ищет `catch`-блоки, которые не пишут в журнал, не бросают
   дальше и не возвращают ошибку пользователю. Нашлось 145; значимы те, что стоят в пути
   данных, а не в отрисовке.
3. **Прочитать все задачи планировщика** (`routes/console.php`) и спросить про каждую:
   что будет, если она упадёт, и кто об этом узнает.
4. **Проверить, что планировщик вообще работает** и куда уходит его вывод.
5. **Сверить показания приборов с действительностью.** Для каждой зелёной проверки на
   странице «Состояние» спросить: что именно она измеряет и может ли быть зелёной при
   сломанной сути. Так нашлась выключенная копия почты.
6. **Посмотреть журналы systemd у периодических служб** — не «запустилась ли», а
   «сделала ли дело». `sa-update` каждый день рапортовал успех, ничего не обновляя.
7. **Проверить глубину хранения журналов**: если следов не остаётся, разбирать будущие
   жалобы будет нечем.

Полезные команды (все выполнялись на .111):

```
sudo zgrep -h "sasl_username=<ящик>" /var/log/mail.log /var/log/mail.log.1
sudo zgrep -h "imap(<ящик>)" /var/log/dovecot/*
sudo doveadm fetch -u <ящик> "uid flags date.sent date.received hdr.to hdr.subject" mailbox Sent
sudo doveadm mailbox status -u <ящик> messages Sent
sudo systemctl cat <служба>; sudo journalctl -u <служба> -n 30 --no-pager
sudo logrotate -d /etc/logrotate.conf 2>&1 | grep -iE "duplicate|error"
cd /opt/mailadmin && sudo -u www-data env HOME=/tmp php artisan tinker <файл.php>
```

Поле `subject` у `doveadm fetch` не существует — правильное имя `hdr.subject`.
Ящик на диске находится через `doveadm user -f home <ящик>` (пути с датой создания,
угадывать их шаблоном бесполезно).

## 4. Что нашли и что с этим сделали

Все правки выложены на оба сервера. Тесты: **56 тестов, 136 утверждений, зелёные**.

### 4.1. Пустые вложения выдавались за настоящие файлы → `28b2771`

Мобильный клиент при обрыве связи оставляет в письме заголовки вложения с `size=0` и
пустым телом. Почта показывала такую часть как обычный файл «1 Б» с кнопками «посмотреть»
и «скачать»: человек скачивал пустышку и решал, что файл испортила почта.

Теперь карточка подписана «файл не дошёл», кнопок нет, в «Скачать все» и в ZIP пустышки
не попадают, над списком стоит объяснение. Порог — 2 байта (пустое тело это один перевод
строки). Правки: `resources/js/mail/attachments.js` (`isEmpty`), `MessageView.vue`,
`MessageReader::attachmentsZip`, `_mail.scss`, справка.

### 4.2. Копия в «Отправленные» терялась молча — в нашем коде → `a77a89d`

`Outgoing::tidyUp` ловил сбой укладки копии и писал только в журнал. Логика «не показывать
ошибку, иначе пошлют второй раз» верная, но следствие — ровно жалоба san, только по нашей
вине.

Сделано: `Outgoing::keepSentCopy()`; при сбое письмо ложится в `storage/app/private/sent-retry/`
и в таблицу `webmail_sent_retry`, команда `mail:sent-retry` (раз в минуту) доносит копию,
**сверяясь по Message-ID**, чтобы не задвоить. После 12 неудач — письмо администратору;
само письмо не выбрасывается.

### 4.3. Отложенная отправка падала с первой попытки → `a77a89d`

`MailOutbox` при любой ошибке ставил `status=failed` навсегда: ни повторов, ни уведомления,
а черновик к тому моменту уже удалён. Значок во «Входящих» считал только `scheduled`, так что
неудача была невидима.

Сделано: 6 попыток с растущей паузой, `attempts` в `webmail_outbox`, уведомление при
окончательной неудаче, значок считает и `failed`. Сбой укладки копии больше не помечает
ушедшее письмо неотправленным (копия ушла в свою очередь из 4.2).

### 4.4. Окно «Отменить отправку» держало письмо только во вкладке → `a77a89d`

5 секунд письмо существовало исключительно в браузере. При уходе со страницы оно досылалось
через `fetch(keepalive)`, а тот **не тянет тела больше ~64 КБ** — письмо с вложением
терялось всегда, и `.catch(() => {})` это проглатывал. Тост при этом уже сказал
«Письмо отправлено».

Сделано: перед отсчётом письмо сохраняется в черновики (`keepDraft`, с `draftKeepFiles`,
чтобы не заливать вложения дважды), тост говорит «Отправляем…» до подтверждения сервера.

### 4.5. Зелёная лампочка на выключенном копировании почты → `a77a89d`

Проверка «Резервная копия» смотрела только на статус задачи. Задача отрабатывала успешно,
но в копию входили лишь база и конфиги (8 МБ в сутки) — пункт «Почтовые ящики» выключен.
Добавлена отдельная проверка состава копии и `Disk::sameDevice()` — копия на том же разделе,
что и почта, от потери диска не спасает.

### 4.6. Об ошибках никто не узнавал → `8fee471`

17 и 18 сентября `sa-update` не мог достучаться до зеркал, правила антиспама не обновлялись
десять дней. `spamassassin-maintenance.service` оба раза отчитался «Finished successfully»
(обёртка выходит с нулём). Страница «Состояние» честно горела жёлтым — не увидел никто:
письма администратору слал другой механизм, знавший только про очередь, диск, службы,
сертификат и копии.

Сделано: `Alerts::check()` теперь поднимает **все красные проверки** страницы «Состояние»
в тот же канал уведомлений. Правила антиспама старше двух недель считаются поломкой.

### 4.7. Журнал Postfix жил вчетверо меньше журналов Dovecot → `8fee471`

`mail.log` лежал в общей пачке `rsyslog` (4 недели), журналы Dovecot — 10 недель. Сегодняшний
разбор упирался ровно в это. `mail.log` переведён в `/etc/logrotate.d/mailadmin`, хранение 10
недель; `update.sh` убирает его из пачки rsyslog (две записи об одном файле logrotate не
допускает и **пропускает весь файл настроек**).

### 4.8. `update.sh` обновляет сам себя → `a39b347`

Bash читает скрипт по мере выполнения, поэтому правки в самом `update.sh` применялись только
со следующего запуска. Из-за этого logrotate полдня простоял с дублем и не ротировал ничего
системного. Теперь скрипт сверяет свою контрольную сумму до и после `git pull` и
перезапускается по новой версии.

### 4.9. Поиск не заглядывал в общие папки, «Спам» и «Корзину» → `7ee99ac` (ранее)

«Найдено 0 во всех папках» при письме, лежащем в «Отправленных» общего ящика. Плюс имя общей
папки собиралось из пути и превращалось в «su» (адрес владельца резался по точке).

## 5. Что сознательно НЕ сделано

Записано в [`TODO.md`](../TODO.md) с причинами. Кратко:

1. **Серверная копия отправленного в «Отправленные»** (`sender_bcc_maps` + разбор служебного
   ящика со сверкой по Message-ID). Это полное лечение случая san — сейчас копию кладёт
   клиент, и сторонние клиенты будут ронять её и дальше. Отложено: скрытая копия добавляет
   письму получателя, и недоступность служебного ящика отложит отправку у всех.
2. **Резервная копия самой почты.** 188 ГБ не копируются никуда; свободно на том же разделе
   176 ГБ, то есть просто включить нельзя — копия добьёт диск. Владелец решил вернуться к
   этому после отладки почтовика. **До тех пор система живёт без возможности восстановления
   после потери диска — это главный оставшийся риск, и он принят сознательно.**
3. **Второй канал уведомлений.** Всё уходит почтой; в аварии «почта не работает» канал не
   работает тоже. Нужен Telegram или SMS, точка врезки — `Alerts::send()`.

## 6. Чем проверять, что ничего не сломано

```
sudo bash /opt/mailadmin/deploy/update.sh     # выкладка (сам перезапустится, если обновился)
sudo bash /opt/mailadmin/deploy/test.sh       # 56 тестов на отдельной копии
python ux/_e2e.py                             # сквозная проверка, результат в ux/_e2e.txt
python ux/_undo.py                            # окно «Отменить отправку», результат в ux/_undo.txt
```

Сквозная проверка проходит отправку, доставку, чтение, скачивание вложения, поиск по теме и
по имени файла, флажок, удаление — в собственном ящике, наружу ничего не уходит, за собой
убирает. `ux/_undo.py` за собой **не** убирает: проверочное письмо надо удалить руками.

### Грабли, на которые уже наступали

- **Octane держит код и манифест сборки в памяти.** Выкладка «руками» (`git pull` +
  `npm run build`) без перезапуска воркеров даёт белый экран: страница ссылается на удалённые
  файлы сборки. Только `deploy/update.sh`.
- **Bash-heredoc портит обратные слэши.** Все правки исходников делаются python-скриптами,
  написанными файловым инструментом, с проверкой «нашлось ровно один раз».
- **`ux/probe.py: run()` возвращает строку**, её надо печатать или писать в файл; вывод с
  типографскими символами не влезает в консоль cp1251 — писать в файл.
- **`shot.py` понимает только шаги `goto`, `js`, `wait`, `shot`, `console`, `net`.** Никаких
  `click` и `go` — их он молча игнорирует.
- **Поиск по заголовкам в Dovecot не работает**, когда включён `fts_enforced = body`:
  `HEADER Content-Type ...` возвращает пусто. Поэтому «есть:вложение» и «файл:» разбирают
  BODYSTRUCTURE, а не ищут по заголовкам.
- `php artisan tinker --execute` через ssh ломается на кавычках — класть скрипт в файл и
  запускать `tinker <файл>`; нужен `HOME=/tmp`, иначе psysh ругается на права.

## 7. Что проверить при повторном разборе

Список того, куда я **не** дошёл или дошёл поверхностно. Это подсказки, а не выводы:

1. **Приём почты.** Разбор шёл со стороны отправки. Правила (sieve), сортировка по папкам,
   карантин, серый список — там та же схема «второй шаг»: если правило не встало, письма
   тихо лежат не там. Смотреть `SyncSieveRules`, `SenderRules`, `QuarantineController`.
2. **Квоты отдельных ящиков.** Диск целиком под наблюдением, а переполненный ящик одного
   человека — нет. При достижении квоты входящие отбиваются. Есть `deploy/postfix-quota-soft.sh`,
   его поведение я не проверял.
3. **DAV (календари и контакты).** `DavStore` — самый крупный файл в проекте, 919 строк,
   в разборе не участвовал. Там свои «вторые шаги»: приглашения, общий доступ, синхронизация.
4. **Черновики.** Автосохранение раз в полминуты; что происходит при сбое сохранения и видит
   ли это человек — не проверял.
5. **Восстановление.** Резервные копии базы делаются, но **восстановление ни разу не
   проверялось**. Копия, из которой не разворачивались, — это предположение, а не копия.
6. **Fail2ban.** Может заблокировать сотрудника с неверным паролем в клиенте; видно ли это
   администратору внятно — не смотрел.
7. **Сертификаты.** Автопродление есть, предупреждение за 14 дней есть; сам факт успешного
   продления в боевых условиях не наблюдался.
8. **145 проглоченных `catch`** из `scan_catch.py` я разобрал выборочно — по пути отправки.
   Стоит пройти остальные, особенно в `app/Services/Dav/` и `app/Http/Controllers/Mail/Api/`.

## 8. Как устроен код (чтобы не искать заново)

Почтовое ядро разложено по частям, `MailStore` — фасад, который делегирует и сохраняет
прежние вызовы для контроллеров:

```
app/Services/Mail/
  MailStore.php       352  фасад
  FolderTree.php      530  папки, роли, общие папки, квота
  MessageListing.php  573  списки, порядок, отбор, поиск
  MessageReader.php   679  чтение письма, переписка, вложения
  MailActions.php     329  флаги, перенос, удаление, дописывание
  MessageSummary.php  166  строка списка
  Structure.php       421  разбор BODYSTRUCTURE
  Outgoing.php        458  сборка и отправка письма
```

Фронтенд веб-почты: `resources/js/Pages/Mail/Inbox.vue` (744) плюс композаблы в
`resources/js/mail/`: `useColumns`, `useUrlState`, `useLiveUpdates`, `useMessageActions`,
`useCompose`, `useHotkeys`.

**Ловушка при работе с композаблами:** значения, разобранные из композабла, созданного ниже
по файлу, нельзя передавать в композабл, созданный выше, — временная мёртвая зона даёт белый
экран. Передавать обёрткой: `undoSend: () => undoSend()`. Так уже ломали боевую почту на две
минуты, и тесты этого не ловят — ловит только браузерная проверка.
